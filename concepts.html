ENTRY · Core architecture decisions

Controllers vs. Minimal APIs

ASP.NET Core has shipped two ways to define HTTP endpoints since .NET 6: Minimal APIs (endpoints mapped directly on the WebApplication instance, e.g. app.MapGet(...)) and the older, class-based Controllers (attribute-routed classes inheriting ControllerBase). Both compile down to the same underlying pipeline — the difference is entirely in how the endpoint code is organized and written, not in what it's capable of.

Why it mattered here

Microsoft's own docs now steer new projects toward Minimal APIs, but this project is modeling what you'd actually be dropped into at a company running an established Angular + .NET + Postgres stack — and controllers are still the foundation of most long-lived enterprise ASP.NET Core codebases. They also force more of the classic C# surface (attributes, constructor-injected dependencies, model binding) that's worth having reps on before an interview testing exactly that.

vs. Minimal APIs

Minimal APIs win for small services where a controller class is pure ceremony — less boilerplate, faster startup, endpoint and logic in one file. For a multi-entity API with several related endpoints per resource, controllers' grouping and filter/attribute pipeline earn their keep back.

ENTRY · Core architecture decisions

EF Core naming vs. PostgreSQL naming

By default, EF Core names database tables and columns after C# classes and properties exactly as written — a Vehicle class with a LicensePlate property becomes a "Vehicle" table with a "LicensePlate" column, PascalCase intact. PostgreSQL, unlike SQL Server, lowercases any unquoted identifier, so the moment a schema has a mixed-case name, Postgres — and every tool that talks to it directly (psql, pgAdmin, raw SQL) — has to wrap it in double quotes to preserve that casing, every single time.

Why it mattered here

This project targets Postgres specifically, so the mismatch surfaces the moment the first migration runs. Fixed once, at the provider level, with the EFCore.NamingConventions package's .UseSnakeCaseNamingConvention() — C# stays PascalCase (Vehicle, LicensePlate), the generated schema is plain snake_case (vehicle, license_plate), and nothing downstream ever needs a quoted identifier.

vs. Fighting it manually

The alternative is decorating every entity with [Table("vehicles")] and every property with [Column("license_plate")] — it works, but it's N annotations for N columns, repeated for every new entity. One provider-level convention replaces all of that with a single line in the DbContext setup.

ENTRY · Domain modeling & EF Core setup

Enum Storage: String vs. Integer Mapping

In C#, an enum is backed by an underlying integer by default (0, 1, 2...). When EF Core maps an enum property to a relational database, its default behavior is saving that integer directly into an INT column. However, using `.HasConversion()` in EF Core instructs the model mapper to serialize enum values as their exact string names ('Available', 'Reserved') when writing to the database, and parse them back to the strongly-typed enum when querying.

Why it mattered here

Storing integers is fragile: if a developer later inserts a new enum member in the middle or reorders the members, every existing row in the database silently points to the wrong domain status without throwing an error. Storing strings guarantees readability in raw SQL tools (pgAdmin, psql) and immune refactoring safety.

vs. Integer Enum Mapping

Integer mapping saves a few bytes of storage per row and indexes marginally faster, but introduces severe silent-corruption risks during long-term schema evolution and makes raw SQL inspection obscure.

ENTRY · Domain modeling & EF Core setup

EF Core Navigation Properties & Nullable Reference Types

Navigation properties in EF Core represent foreign-key relationships directly on domain classes. Instead of manually joining raw IDs, a Vehicle entity exposes an `ICollection` property representing all related child records. In modern C# with Nullable Reference Types enabled (`#nullable enable`), non-nullable string and collection properties must be initialized (e.g. `= string.Empty;` or `= new List();`) to eliminate NullReferenceExceptions at compile time.

Why it mattered here

Initializing collection navigation properties to an empty list ensures that querying a Vehicle with no reservations yields an empty collection instead of null, preventing defensive null-checks throughout the service layer. Using the interface `ICollection` rather than a concrete `List` allows EF Core's change tracker to inject its own proxy or notification collections if needed.

Object-Relational Mapping (ORM) & EF Core

An ORM (Object-Relational Mapper) is a software layer that translates between object-oriented code (C# classes, properties, collections) and relational database structures (SQL tables, columns, foreign keys). Entity Framework Core (EF Core) is Microsoft's official modern ORM for .NET. Instead of writing manual SQL strings (`SELECT * FROM vehicles`) and manually mapping database result sets into C# objects, EF Core lets developers query and persist data using strongly-typed C# LINQ syntax.

Why it mattered here

EF Core manages schema migrations, connection pooling, SQL generation, and change tracking out of the box, drastically reducing boilerplate data-access code and eliminating common SQL injection vulnerabilities while keeping our domain logic in pure C#.

vs. Raw ADO.NET / Micro-ORMs (Dapper)

Raw ADO.NET and micro-ORMs like Dapper offer maximum query execution performance and explicit raw SQL control, but require writing and maintaining all SQL schemas, joins, and parameter mappings by hand.

PostgreSQL UTC Timestamps (`timestamptz`) & Npgsql

PostgreSQL provides two main timestamp types: `timestamp without time zone` (`timestamp`) and `timestamp with time zone` (`timestamptz`). In modern backend architecture, all server-side dates (such as reservation start and end times) should be stored in Universal Coordinated Time (UTC). The Npgsql EF Core provider strictly enforces this: if you pass a C# `DateTime` whose `.Kind` property is `Unspecified` or `Local`, Npgsql throws a runtime exception to prevent timezone-shift bugs.

Why it mattered here

Reservations and maintenance windows deal with time-overlap logic across potentially different timezones. Storing all dates in UTC guarantees unambiguous intervals and deterministic overlap comparison queries in SQL.

vs. Local Time / Timestamp without Timezone

Storing local timestamps leads to catastrophic bugs during daylight saving transitions and makes comparing times from users in different timezones impossible without error-prone client-side conversions.
